# Session and Authentication Token Storage

## 1. Subsystem Description

The Session and Authentication Token Storage subsystem manages user login sessions in an application. When a user logs in successfully, the application creates a session and associates it with that user. The session helps the backend identify the user across subsequent HTTP requests. The database stores a hash of the session token instead of the original token, along with timestamps that help the application determine whether the session has expired or been revoked. A user can have multiple active sessions, such as one on a laptop and another on a mobile phone.

## 2. Table Design

### Users1 Table

The `users1` table stores account information.

- **id:** A UUID generated by PostgreSQL that uniquely identifies each user. It is the primary key.
- **username:** Stores the user's username. It is `NOT NULL` and `UNIQUE` to prevent missing or duplicate usernames.
- **password_hash:** Stores the cryptographic hash of the user's password instead of the original password.
- **created_at:** Records when the account was created. It defaults to the current timestamp.
- **updated_at:** Records the account's last update time. It defaults to the current timestamp when the row is created. Updating it automatically on later changes requires additional logic.
- **deleted_at:** Supports soft deletion. A non-null value indicates that the account has been marked as deleted without physically removing its row.

### Sessions Table

The `sessions` table stores individual login sessions.

- **id:** An automatically generated integer primary key that identifies each session row.
- **token_hash:** Stores a hash of the session token. It is `NOT NULL` and `UNIQUE` so that duplicate token hashes cannot be stored.
- **user_id:** A UUID foreign key referencing `users1.id`. It identifies the user who owns the session.
- **created_at:** Records when the session was created.
- **last_seen_at:** Records the last activity time. The application must update this value when activity is recorded.
- **expiry_at:** Stores the absolute expiry time of the session.
- **idle_expiry_at:** Stores the idle-expiry deadline, after which the session should be considered invalid if the application enforces this rule.
- **revoked_at:** Stores the time when a session is revoked. A non-null value indicates that the session has been revoked.

## 3. Foreign-Key Relationship

The `sessions.user_id` column references `users1.id`. This establishes a one-to-many relationship: one user can have multiple sessions, but each session belongs to one user.

The `ON DELETE CASCADE` constraint automatically deletes a user's session rows when that user's row is physically deleted. This does not apply when the account is only soft-deleted by setting `deleted_at`.

## 4. Design Trade-offs

UUIDs are used for user identifiers because they provide unique identifiers without requiring sequential user IDs. Session rows use automatically generated integers because they are internal database identifiers. The original passwords and session tokens are not stored; instead, their hashes are stored to reduce exposure if the database is compromised. Passwords should be hashed using a suitable password-hashing algorithm, and session tokens should be generated securely and handled carefully by the application.

Soft deletion preserves account records, which can be useful for auditing or recovery, but requires application queries to exclude deleted accounts where appropriate. Cascading deletion simplifies removal of session rows when an account is physically deleted, but it also means those session rows cannot be retained after that deletion.

## 5. Indexing

PostgreSQL automatically creates indexes for primary keys and unique constraints. Therefore, the primary keys on `users1.id` and `sessions.id`, along with the unique constraints on `users1.username` and `sessions.token_hash`, have supporting indexes.

An additional index, `sessions_user_id_idx`, supports queries that retrieve all sessions belonging to a particular user. The `sessions_expiry_at_idx` index can help queries that search for sessions by their absolute expiry time.

Indexes can speed up lookups but require additional storage and add overhead to inserts, updates and deletes. Their usefulness should be evaluated against actual query patterns and table sizes.

## 6. Normalization

### First Normal Form (1NF)

Each column stores a single value, and each session is represented by its own row. A user with multiple sessions does not need a list of sessions stored in one column.

### Second Normal Form (2NF)

Each table has a single-column primary key. Its non-key attributes describe the entity identified by that key, rather than depending on only part of a composite key.

### Third Normal Form (3NF)

User account details are stored in `users1`, while session-specific details are stored in `sessions`. Username and password hash are not repeated in every session row. The foreign key links each session to its user, reducing unnecessary duplication and update anomalies.

## 7. PostgreSQL-Specific Features

The schema uses PostgreSQL's `UUID` type, `gen_random_uuid()` for UUID generation, `GENERATED ALWAYS AS IDENTITY` for session IDs, `TIMESTAMPTZ` for timestamps with time-zone awareness, and `now()` for default timestamps.

The `updated_at` column does not automatically change on every update in the current schema. A trigger or application logic would be needed for that behavior. Likewise, the application must enforce session expiration, idle expiration, revocation, and account soft-deletion rules when validating requests.
